# Kelp vertical implementation plan

Last updated: 2026-07-30

This is the canonical delivery sequence for work across Codex tasks. Detailed domain behavior lives in [`docs/product/product-contract.md`](docs/product/product-contract.md); historical planning documents are reference material only.

Every phase follows the same completion track:

> Inspection → schema and RLS → server commands and projections → frontend → tests → concise documentation

A phase is complete only after its applicable static checks, local database characterizations, and residue audit pass.

### Permanent automated-verification lane

Every product phase ends with an explicit automated verification and security checkpoint. Existing labels such as `4.F`, `5.I`, and `6.F` retain their names; phases without a final verification label receive an `X.V — Automated verification and security checkpoint` before they can be marked complete. This checkpoint is implementation work, not a documentation-only review.

Each checkpoint must, where applicable:

1. run source/contract checks for browser and server adapters;
2. run hostile-actor database characterizations for every participating role, including direct-table and RPC attempts;
3. replay the complete migration chain from an empty database and apply the newest migration to the retained local stack;
4. verify stale-state, concurrent-decision, idempotent-retry, rollback, immutable-history, and timezone/date-boundary behavior;
5. inventory new tables, views, functions, Storage buckets, grants, and RLS policies;
6. scan frontend and generated browser assets for service-role keys, secret keys, private credentials, and other server-only configuration;
7. run the deterministic-actor residue audit and record the result in the acceptance log.

**Bug-to-regression rule:** whenever diagnosis identifies a product defect or a test/harness defect, the fix must add the smallest durable regression that reproduces the original failure. Earlier regressions remain in the consolidated suites. This specifically includes the failures already found around deferred constraints and pending trigger events, partial migration application, `psql` variables inside dollar-quoted blocks, ambiguous PL/pgSQL identifiers, stale-version precedence, exact-retry idempotency, duplicated target signatures, Course-date authority, viewer-local date boundaries, legacy source identity, immutable Studied/history retention, RLS/grant mismatches, actionable Calendar destinations, and branch-qualified module identity/colors.

Phase ownership for the new security cases is:

| Security invariant | Owning checkpoint | Required characterization |
| --- | --- | --- |
| A newly created user cannot promote themselves to Tutor or Mentor | Phase 1.V; reconfirmed in Phases 16.V and 17.V | Sign-up always creates only the baseline Student role; direct `profiles`/`user_roles` writes and self-targeted role-grant RPC calls fail; only the governed application/authorization workflow can add a teaching role. |
| A Student cannot edit administrative Profile fields | Phase 1.V | Student updates to role, status, verification, provider, organization, qualification, audit, and server-derived timezone fields fail while explicitly editable personal fields still succeed. |
| A Tutor cannot view Students not assigned to them | Phase 3.V; reconfirmed after reassignment in Phase 6.V | Assigned-Student reads succeed; another active Student's Profile, Course, Classroom, Schedule, Files, Exams, and derived summaries remain absent or denied before and after reassignment. |
| A Tutor cannot directly start or close a live Class | Phase 12.V | Tutor room entry and post-lesson reporting do not grant lifecycle mutation; direct start/complete/close writes fail, while the governed presence/system command performs eligible transitions. |
| A Mentor may act only on subordinate Tutors | Phase 6.V; reconfirmed in Phases 8.V and 17.V | Same-hierarchy actions succeed; equivalent actions against an unrelated or differently scoped Tutor fail atomically without notifications or audit side effects. |
| Audited users cannot modify their audit logs | Every phase that adds an audit/event table; global confirmation in Phase 18.V | The audited actor may receive only its redacted read projection; direct insert/update/delete and mutation through unintended RPCs fail. Append-only events are created only by the governed command. |
| A Teacher cannot access Exams, Schedules, or Files belonging to another organizational unit | Phase 17.V, with resource-ownership precursors in Phases 4.V, 5.V, and 7.V | Same-unit authorized access succeeds; cross-unit direct-table, RPC, Storage listing, signed-link, and guessed-ID attempts fail without revealing whether the resource exists. |
| All new private tables and buckets have RLS enabled | Every phase checkpoint; global confirmation in Phase 18.V | Catalog-driven inventory fails the suite for any unregistered table/bucket lacking RLS and least-privilege policies. Any deliberately public lookup object requires an explicit reviewed allowlist entry. |
| No service-role key or secret key appears in frontend code | Every phase checkpoint; global confirmation in Phase 18.V | Static scan covers source HTML/CSS/JS, generated Track pages/data, committed fixtures, and browser bundles; only publishable client configuration may appear. |

Non-blocking Assignment and milestone detail may be visually de-emphasized, but booked Classes remain visible as conflicts.
- The Student selects an eligible Slot from the overlay before the request form opens. The form then receives the Tutor and Slot as fixed context and collects the relevant Subject/Course, purpose, duration, and optional details. Month, Week, and Timeline may seed the Calendar position, but they must not bypass Tutor selection or open an all-at-once form before a Slot is chosen.
- The overlay is transient and never reserves a Slot by itself. It is dismissed after a successful request, cancellation/abandonment, Tutor-context change, or departure from the booking workflow so Tutor availability cannot be mistaken for the Student's own Calendar.
- The overlay must distinguish available time, unavailable time, the Student's conflicts, and any permitted competing-request/queue indication without exposing another Student's identity or private Tutor unavailability reasons.
- The Dashboard/global Calendar may browse Tutors authorized by the Student's active relationships and the later availability and matching contracts. A Classroom Calendar uses the same interaction but preselects and locks that Classroom's current assigned Tutor.

- **10.V — Calendar/request security and regression checkpoint.** Verify relationship-scoped Tutor discovery, privacy-safe availability, cross-Student request denial, slot-race and stale-overlay handling, exact retry behavior, independent Assignment deadlines, timezone/DST boundaries, attachment isolation, RLS inventory, secret scan, rollback, and residue audit.

### Phase 12 — Live Class lifecycle

Scheduled access, pre/post-lesson forms, attendance, completion, no-shows, outages, credit charge/release, Tutor settlement inputs, and Class history.

Verify Student/Tutor attendance combinations, technical/outside-Kelp evidence, reporting deadlines, disputes, credit recommendations, settlement holds, immutable occurrence history, RLS/private-bucket inventory, secret scan, rollback, and residue audit.

The control remains disabled until the report authority and document pipeline are implemented in this phase.

## Dependency path

The central delivery dependency is:

> Course Schedule → availability and Tutor assignment → Assessment delivery → Intake activation → Calendar booking → credit validation → live Class lifecycle

Later features must consume these authorities rather than recreating parallel browser-owned state.
